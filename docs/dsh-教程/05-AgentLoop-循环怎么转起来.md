# 第 5 章 Agent Loop：循环是怎么转起来的

> 前几章我们搭好了"账本"和"窗户"，这一章装**发动机**：Agent Loop（循环驱动器）——它让模型和工具"你来我往"地转起来。
> 这是 DSH 里最接近"你以前写的 `while` 循环"的东西，但远比那复杂。读完这一章，你会懂：turn、step、inbox、maintenance……这些词到底在说什么，以及 DSH 是怎么做到"既能自动跑，又能随时停下干点杂活"的。

---

## 5.1 从一张"总循环状态图"开始

**ReactLoopAgent**（DSH 循环的实体）不是只存在"运行"和"停止"两种状态，它有一个更细的状态机，含三个 phase：

```
        ┌────────────┐         ┌─────────────┐         ┌──────────────┐
        │   idle     │ ──────► │  running    │ ──────► │  maintenance │
        │  (空闲)     │  收到消息 │  (运行中)    │  干杂活   │  (维护中)     │
        └────────────┘         └─────────────┘         └──────────────┘
              ▲                      │                        │
              └──────────────────────┴────────────────────────┘
                      干完一件事后，如果没有挂起的消息，回到 idle
```

- **idle（空闲）**：没在干活，等待新消息。
- **running（运行中）**：正在执行 turn（处理消息 → 发请求 → 跑工具）。这是它花大部分时间的状态。
- **maintenance（维护中）**：暂时没在处理用户对话，专心干"后台维护活"（比如手动 /compact 压缩、别的清理任务）。**它不允许和对话循环抢时间。**

为什么要分出 maintenance？因为有些维护工作（比如手动压缩）要求"趁着 Agent 不忙的时候做"，否则会和正在跑的对话冲突。所以 DSH 规定：**只有 idle 状态才允许进入 maintenance。**

---

## 5.2 两个基础单位：turn（轮）和 step（步）

这是最容易懵的地方，先厘清：

- **turn（轮）**：从"Agent 收到一条新消息开始处理"到"它停下等你"为止的一次完整工作。一轮里它可能会发好几次请求。
- **step（步）**：一轮里的"单个来回"——一次"发请求给模型 → 拿到回复 →（如果需要）执行工具调用"。

一个 turn 由多个 step 组成。举个例子：

```
用户："帮我跑这个项目测试"

turn 开始
  step 1：发请求 → 模型说"我先看看目录" + 我要调 list_files
         执行工具：list_files（返回目录）→ 有工具调用，继续
  step 2：发请求（带着目录结果）→ 模型说"我要跑 pnpm test" + 调 run_command
         执行工具：pnpm test（跑起来了）
  step N：发请求 → 模型说"测试通过了，搞定" → 没有工具调用，本 turn 结束
turn 结束，Agent 回 idle
```

**step 每次都要把"到目前为止的 Surface"发给模型**（包括前一步的工具结果），所以模型总是"看着最新进展"继续。这就是 Agent 循环的本质。

---

## 5.3 消息怎么进来？——inbox（收件箱）

你可能好奇：用户的消息怎么进入这个循环？

DSH 给 Agent 配了一个 **inbox（收件箱）**，类似消息队列：
- `send(...)`：往收件箱放一条消息，可以带"要不要唤醒 Agent"参数。
- `splice` / `reserve` / `claim`：按情况从收件箱取消息。

关键巧妙点在于"**唤醒（wakeup）**"逻辑。想象一个场景：

> Agent 正在运行中（running），用户又发来一条消息。此刻 Agent 正忙着，不能立即处理。

DSH 的处理是：把新消息放进收件箱，并且**记一个"要唤醒"的记号（wakeRequested）**。等当前 turn 一结束，Agent 看到"有挂起消息 + 想被唤醒"→ 就**不休息**，立刻开新的一轮处理它。

反之，如果只是一条"补充信息"（steer/inject，不需要新开一轮，只需要在下一步用上），收件箱会处理但不唤醒。这就是 DSH 区分"**开新轮**"还是"**仅下一步用**"的细腻之处。

---

## 5.4 step 是怎么执行的：`preStep` 和 `step`

看代码，一个 step 的执行分两大段：**preStep（步前）** 和 **step（执行步）**。

### preStep：走这一步前，先把"这步要看到什么"准备好

流程是这样的：

1. 从收件箱 `claim` 出这步要处理的消息。
2. 组装 **system prompt**（系统提示）：DSH 会调用 system-prompt 插件把该给模型的系统提示拼好。
3. 拼接**动态上下文**：当前的 cwd、权限等运行环境信息（这块第 5.6 会说）。
4. 触发 `agent/pre-step` 瀑布事件——其他插件可以在这里"插一脚"修改这步的输入。
5. 决定这步的输入消息列表（默认 = 收件箱消息 + 动态上下文）。

如果某个插件在 pre-step 拒绝了这步（reject），本步就作废。

### step：发请求、收流、执行工具

这是"最像 while 循环"的部分：

```
while (true) {
  // 1. 从日志算出"模型到目前为止该看到什么"（deriveMessages）
  // 2. 构建请求：system + tools + messages
  // 3. 流式发送给模型，逐块记录 assistant/chunk
  // 4. 模型回应：
  //    - 如果只有文本回复，没有工具调用 → 本步骤完成
  //    - 如果有工具调用 → 第 6 章的工具调度器去执行；执行完结果回到下一步
  //    - 如果 max-tokens 截断 → 标记"这步被截断"
}
```

注意第 1 步：**每次发请求前，DSH 都重新从日志算一遍模型该看到的 Surface**（`deriveMessages`）。这意味着"模型看到的东西"永远是**基于账本实时推导**的，不靠你手动维护一个 messages 数组。这就是"事件日志是唯一真相"在循环里的体现。

---

## 5.5 挂起的细节：每个事件都落账

学习 DSH，你会发现它**极度在意"每一步都被记录"**：

- 每轮开始：写 `turn/start`
- 每步开始：写 `step/start`
- 每一条用户消息：写 `user/message`（append 到 Surface）
- 每个流式碎片：写 `assistant/chunk`
- 模型说完：写 `assistant/message`（并记下它对应哪些 chunk 的 seq——`sourceEventSeqs`）
- 工具调用/结果：写 `tool/call`、`tool/result`
- 每步结束：写 `step/end`
- 每轮结束：写 `turn/end`，并记录这一轮怎么结束（完成？被中止？报错？）

为什么要这么啰嗦？回第 3 章：**账本完整，才能重放、复现、审计、对齐缓存。** 你甚至可以这样理解：DSH 的循环，本质上就是"每做一件事，就往账本上写一行，然后基于账本再算下一步"。

---

## 5.6 动态上下文：绝不污染 system prompt 前缀（重要！）

这是 DSH 缓存哲学里一个非常"反直觉但极聪明"的设计，提前剧透一点（第 8 章会深入）：

**问题**：Agent 干活时，当前目录（cwd）、可用权限这种"运行环境信息"经常变。如果把这些**写进 system prompt**……那么 system prompt 每次都在变 → 请求前缀每次都变 → **缓存全废**！

**DSH 的解法**：动态信息**绝不进 system prompt**，而是作为一条"运行时上下文快照"的 `user/message`，**只在内容变化时**才往 Surface 追加一条。如果没变，就不写任何新事件。

这样：
- system prompt 这个"固定前缀"永远稳定 → 缓存友好。
- 动态信息只是对话中间的一条补充消息，变了才加，没变就不加。

这个设计就叫 `runtime-context`（运行时上下文投影）。它完美体现了 DSH 的优先级：**动态的东西，宁可丢在 user 消息里，绝不让前缀 (system) 乱动。**

---

## 5.7 出错怎么办？——每轮结束都有"归宿"

一轮跑完，总要先给个"交代"。DSH 在 `turn/end` 里记录 reason（结束原因），只有这几种：

| reason | 什么意思 |
|---|---|
| `completed` | 正常结束，没有更多要做的 |
| `blocked` | 被某插件在 pre-step 拒绝了，这轮作废 |
| `aborted` | 被中止（比如用户点了停止） |
| `error` | 出错了（比如 LLM 调用失败） |

错误还会拆两类：**可重试的**（比如临时的 LLM 错误，可能走 retry），和**不可知的**（其他异常堆栈会拍平成一个 UNKNOWN error code）。每一轮都清楚交代"我为什么停"，对排错非常友好。

## 5.8 一趟"整车跑"的完整模拟

把这一章串起来，走一遍"用户说：跑测试"：

```
用户点发送
  ▼ send() → inbox 收到消息 + wake
  ▼ 此刻 idle → 进入 running，开 turn
  turn/start
    step 1：
      preStep → claim 消息，拼 system（固定） + 动态上下文（user 快照）
      step/start
      user/message（append）
      发请求（surface = system + 用户消息）
      assistant/chunk xN（流式）
      assistant/message：模型说"我先看目录" + tool/call
      tool/call → 工具调度器执行 list_files
      tool/result → 返回目录清单（append）
      step/end
      还有工具 → 下一 step
    step 2：…（带着目录结果继续）…
      最终 assistant/message 没有工具调用 → completed
  turn/end（reason=completed）
  ▼ 没有待处理消息 → 回 idle
```

## 5.10 下一章预告

循环要"跑工具"，但绑到"谁去跑、怎么并排跑、结果怎么回账"这还没讲。第 6 章我们把镜头对准**工具系统**：多个工具同时跑、结果必须按顺序回、被中止的工具怎么留下"合成错误"……这些细节，全是为了"账本永远成对、可重放"。

> 记住这句话再走：
> **Agent Loop = 状态机(空闲/运行/维护) + 收件箱 + turn/step 两级循环 + 每次请求前从日志重算 Surface；动态信息绝不进 system 前缀，这是缓存友好的铁律。**
