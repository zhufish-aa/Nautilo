# 第 8 章 Prompt Cache：缓存经济学

> 这是全书最"值钱"的一章，也是你之前所有章节里那些"奇奇怪怪的坚持"的真正答案：
> 为什么 DSH 只增不改？为什么动态信息不进 system prompt？为什么 append 是宝贝、replace 是仇人？为什么请求头变了才记？——**全都是为了缓存。**
> 读完这一章，你会拥有一个"缓存视角"，再回看前面的设计，一个个都能对号入座。

---

## 8.1 缓存是什么？先花 30 秒理解它为什么值钱

想象你写作文。老师（模型）每次批改，都要把你交的稿子从头读一遍。

- 如果你的稿子**每次都变动**（哪怕只改最后一段前面全一样），老师是不是还得从头读？——浪费。
- 如果老师**记住了**你前面 10 页的内容，只认真读新加的那一页呢？——快多了。

Prompt Cache（提示词缓存）就是这个"老师的记忆"。模型服务商（比如 DeepSeek、OpenAI）在计算你的请求时，会缓存**已经算过的前缀**。下次你发的前缀和上次完全一致，服务商直接复用缓存，**不用重新算这些 token**。

**为什么"值钱"？两个词：**
1. **省时间**：缓存命中的部分不用重新计算，响应更快（尤其前缀很长时，差距巨大）。
2. **省钱**：很多厂商对缓存命中的 token 大幅降价（可能打 1 折甚至更低）。命中越多，越便宜。

所以概括起来一句话：

> **请求前缀越稳定，缓存命中越多，Agent 跑得越快、越便宜。** 这就是整本书的最核心价值观。

---

## 8.2 缓存命中的两个必要条件

要让缓存命中，必须同时满足两个条件：

1. **前缀字节完全一致**：缓存是"字节级"匹配。你中间哪怕多了一个空格、改了一个字段顺序，从那个位置往后的缓存就全作废。
2. **前缀足够长**：太短的前缀（比如就一句话）不值得缓存，服务商通常只对一段有分量的前缀给缓存待遇。

再看 DSH 的做法为什么教科书级——它把所有力气都花在"让前缀尽量长且稳定"上。

---

## 8.3 再看一次那几道"怪设计"，这次用缓存视角

### 设计①：只增不改的日志 → 前缀稳定
第 3 章我们只知道"只增不改 → 可重放"。现在补上另一半：

> 只增不改 → 历史永远不变 → 每次新请求 = 老前缀 + 新尾巴 → **老前缀命中命中命中！**

如果日志允许"改历史"，那每次循环前一大堆都变了，缓存全废。这是 DSH 选"账本"而不是"可编辑数据库"的**真正战略原因**。

### 设计②：动态信息不进 system prompt → 保住"最前面的缓存"
第 5.6 章那个"动态上下文放 user/message"的怪设计，缓存想一下就懂了：

> 请求的开头是 system prompt。如果 cwd、权限这些**天天变**的东西写进 system，那 system 每次变 → **整个前缀开头就变了** → 全文缓存报销。

放在 user/message 里呢？system 前缀稳定；动态信息只是对话中间，只在变化时才加一条——**绝大多数时候前缀根本不动**。DSH 宁可把功能上"系统级"的信息塞进 user 消息，也要让 system 前缀一块砖都不动。这就是缓存优先级的极端体现。

### 设计③：请求头变了才记 → 头（前缀最前）必须稳
第 3.6 章的 `request/header` "变了才记"。缓存视角：请求头 = 前缀最前面的那十几行。如果每次请求都重新生成一个"看起来一样但字节不同"的头，前缀第一段就废了。

所以 DSH 极严格地用 `headerEquals` 逐项比较，**哪怕参数顺序都一样，也不生成新头**。它宁可"重复利用旧头"，绝不制造"相同语义但不同字节"的新头。

### 设计④：tools / system 一旦定下就不乱动
tools（工具定义）和 system prompt 是请求前缀的大头。DSH 的逻辑是：**一旦一套 tools 定了，就不改**（或者尽量少改）。因为 tools 一变，前缀全变。

（这也是为什么工具 schema 必须"确定性序列化"——同样的 tools 永远生成同样的字节。第 10 章讲压缩时你还会看到"复用最近请求的 system+tools"这个天才操作。）

## 8.4 举个具体数字，感受缓存的价值

假设上下文窗口 128K，每次请求前缀约 100K token（大量工具定义 + 历史）。厂商缓存命中价约为非命中的 **1/10**。

- 缓存命中率 0%（前缀每次都变）：每次花 100K 的全价。
- 缓存命中率 80%（前缀稳定，只新增 20K 新内容）：100K 里 80K 打一折。

同样的活，成本差出好几倍。而且**速度**也差出好几倍——长前缀重新计算的耗时是用户直接感受得到的。

这也解释了 DSH 为什么要做第 7.4 的那个统计：**它必须能算出"我缓存命中率多少"**，才知道自己的前缀策略有没有生效，才能持续优化。

---

## 8.5 DSH 有个专门的测试：验证缓存真的命中了

这不是一句空话——DSH 源码里有一个**真实的端到端测试**（`request-cache.e2e.ts`），它会连接真实 API 发一串请求，然后断言：

> "第一个请求之后，**每一个**请求的 cacheReadTokens 都必须 > 0。"

也就是说：它**用真金白银**验证"我们的循环确实让缓存每次都命中"！如果不命中，测试直接失败。这种"把缓存友好当成可验证的正确性要求"的态度，是 DSH 与普通"能跑就行"的循环最本质的区别。

你可以把这个测试当成本章最有力的证据：**缓存友好不是口号，是 DSH 的验收标准。**

---

## 8.6 缓存与压缩的"相爱相杀"（预告）

现在你知道了缓存的规则，我们提前埋一个以后要解的结：

**问题**：对话太长必须压缩（第 9 章）。但压缩要用 replace 把中间一段历史换成 summary——而 replace 会让后面缓存全废！

**DSH 的解**（第 10 章是重头戏）：压缩**不破坏请求前缀**——压缩时发的摘要请求，复用"最近一次真实请求的 system + tools + 被压部分派生消息"做**前缀**，只在最末尾追加一段指令。这样连"压缩请求本身"都命中了缓存！压缩完之后的**后续请求**也会复用"带 summary 的新前缀"。

一句话：**DSH 连"让对话变短"这件事，都用缓存友好的方式去做。** 这个细节是整个压缩系统最精妙的部分。

## 8.7 一张"缓存友好 vs 缓存杀手"对照表

| 行为 | 对缓存 | 为什么 |
|---|---|---|
| 只增不改的日志 | ✅ 友好 | 前缀稳定，历史不变 |
| append 新消息 | ✅ 友好 | 老前缀 + 新尾巴，全命中 |
| 动态信息放 user 消息（变了才加） | ✅ 友好 | system 前缀不动 |
| 请求头严格去重（变了才记） | ✅ 友好 | 头 = 前缀最前，必须稳 |
| tools / system 一旦定下不乱动 | ✅ 友好 | tools 是前缀大头，动则全废 |
| replace（压缩砍段） | ⚠️ 注意 | 从替换处起缓存作废，需用摘要前缀复用技术补救 |
| 每次请求重新拼一个"语义相同字节不同"的 system/tools | ❌ 杀手 | 字节不一致 = 缓存全作废 |
