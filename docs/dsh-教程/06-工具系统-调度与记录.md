# 第 6 章 工具系统：调度与记录

> 第 5 章循环转起来了，但"模型说要调用工具"之后，工具到底怎么被执行、结果怎么回去、多个工具怎么同时跑还不乱套——正是这一章。
> 工具系统的难点不在"调用"，而在**并发与顺序**：工具可以并行跑（省时间），但结果必须**按模型要求的顺序**进账本（否则模型看到错乱的上下文）。这一章就看 DSH 怎么把这两件事都不耽误。

---

## 6.1 一个模型回复里可以有多个工具调用

先纠正一个直觉：模型一次回复，不只允许调用一个工具。它可能一口气说：

```
assistant/message：
  "我同时做两件事："
  tool_call #1: 读 package.json
  tool_call #2: 读 src/index.ts
```

这两个调用是**并行**的（没有依赖），DSH 想让它们同时跑，节省时间。

但问题来了：**工具跑完了，结果该怎么回给模型？**

如果两个工具同时跑，先回来的先写账本 → 那账本里顺序可能就是"package.json 结果 → src/index.ts 结果"；但模型明明是**先声明了 #1 再 #2**。如果结果顺序和模型声明的顺序不一致，模型会懵："我先要的 #1 的结果怎么排在后面？"

**结论：工具执行可以并行，但结果入账必须按模型声明顺序。**

这就是工具系统最核心的纪律。代码里 `commitReady()` 的意思就是：**只把"轮到它"的那些结果提交入账**——前一个还没就绪，后面的结果就算早回来了也得等着，绝不能插队。

---

## 6.2 三种执行模式

DSH 根据工具的声明，决定它们是"一个接一个"还是"一起上"：

| 模式 | 意思 | 典型 |
|---|---|---|
| `parallel`（并行） | 这一组工具可以同时跑 | 读几个互不相关的文件 |
| 串行（barrier/独占） | 一次只跑一个，跑完再下一个 | 改文件、跑命令等有副作用或依赖顺序的 |

DSH 会把计划中的工具调用**分成组**：能并行的组一起跑，必须串行的组一个个来。这个"分组决策"不是固定的，DDH 会在执行过程中**重新判断**（re-classify）——比如一开始以为能并行，后来发现某个新工具要求串行，就拆开。够小心眼，对吧？为的就是不乱。

---

## 6.3 并行窗口：maxParallelToolCalls

DSH 不是无限并行，它有个上限：`maxParallelToolCalls`（最大并行工具调用数）。

- 如果设为 1：等于所有工具一个个来（相当于全串行）。
- 如果设得大：同一时刻最多有几个工具在跑。

这个数字可以在 Agent 配置里调。你可能会问："为什么不直接无限并行？"因为：你发的请求别把机器打爆、别让结果乱套、也别忘了**成本和负载**。所以 DSH 用一个"滚动池（sliding pool）"：一批跑完补一批，始终控制在限内。

---

## 6.4 记账纪律：对话必须"成对"

工具调用在账本上必须是**成对**出现的：

```
tool/call    ← 模型说要调这个工具
tool/result  ← 这个工具的结果（永远配对！）
```

DSH 用 `sourceEventSeqs: [callSeq]` 记录"这个 result 对应的是哪个 call"。这个配对关系极其重要，因为：

1. **Surface 才能正确显示**：模型看到"工具结果"时，它需要知道这是"哪个工具调用的结果"。
2. **压缩才敢切段**（第 9 章）：压缩要选一段历史压掉，如果不小心把一个 `tool/call` 压掉却没压它的 `tool/result`，那模型会看到"有个结果但没有对应调用"——上下文就坏了。DSH 有个专门的平衡检查（tool-pairing）保证切点不拆开这种问答对。

想象一个"坏了"的场景你就懂了：账本里 `tool/result` 出现了，但它没有对应的 `tool/call`。DSH 会直接判定"surface 坏了"（代码里那句报错：tool/result 找不到匹配的 tool-call = corrupt surface）。**宁可报错，不让账本脏着。** 这就是纪律。

---

## 6.5 中途被中止的工具：合成一个"错误结果"

场景：模型同时调了 3 个工具 #1 #2 #3，用户突然点了"停止"（abort）。

- 已开始跑的（比如 #1 正在执行）：让它们**跑完收尾**（排水），结果照常入账——因为已经进行到一半了，中止会造成不完整。
- 还没开始的（比如 #2 #3）：**不执行**，但 DSH 会为它们**各补一条"合成错误"的 tool/result**：

```
tool/call  #2
tool/result #2   ← 合成错误："Error: tool call aborted before dispatch"（错误码 TOOL_ABORTED_BEFORE_DISPATCH）
```

有没有发现这很妙？**被中止的工具，也在账本里留下了一条成对记录。** 为什么？因为如果不补这条，账本里 `tool/call #2` 就没有对应的 `tool/result`，模型下次看到会困惑（而且配对检查会报错）。补一条合成错误，账本依然成对、可重放、不稀烂。

这就是 DSH 的"宁可留一个假结果，也不留一个坏账本"的思路。

---

## 6.6 工具参数怎么处理？

模型发出的工具参数是一段 JSON 字符串。DSH 会尝试 `JSON.parse` 解析它：

- 成功 → 解析成结构化参数传给工具。
- 失败（模型吐了个不规范的参数）→ **不直接抛错**，而是把**原始字符串**原样传下去（`parseArguments` 的兜底逻辑是 `JSON.parse(raw) catch → raw`）。

为什么不报错？因为有些工具能容忍原始字符串，或者至少让错误更温和地暴露。总之，DSH 尽量"宽容处理模型的低质量输出"，不让整个循环因为一个格式问题崩塌。

---

## 6.7 一条完整的时间线

```
模型回复：我要并行调 tool#1(读A) 和 tool#2(读B)
│
├─ 计划分组：这俩是 parallel → 一组
├─ 并行窗口：maxParallelToolCalls=5 → 两个都不用等，一起上
│
├─ tool/call #1 (seq 100), tool/call #2 (seq 101)   ← 先记调用，顺序固定
│
├─ tool#1 先执行完 → 结果暂存，但【还不能入账】
├─ tool#2 后执行完 → 结果也暂存
│
├─ 现在按模型顺序提交：先 #1 后 #2
│     tool/result #1（sourceEventSeqs=[100]）
│     tool/result #2（sourceEventSeqs=[101]）
│
└─ 两个结果都进了 Surface → 下一步发请求时模型能看到"A 和 B 的内容"
```

**你看：执行是并行的，但入账是按 #1 #2 顺序的。** 这条纪律保证了模型永远看到有序、完整、可配对的上下文。

## 6.8 工具和权限的关系（预告）

工具并不是"随便就能调"。DSH 有 `interaction`（交互/权限）相关的插件：调用一个**有副作用的工具**（比如跑命令、改文件）之前，可能要先经过用户批准。这个机制在第 11 章收尾时会讲到。现在你只需要知道：工具系统管"怎么跑、怎么入账"，权限系统管"能不能跑"。分得很清。
