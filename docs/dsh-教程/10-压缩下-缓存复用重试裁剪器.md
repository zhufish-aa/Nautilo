## 10.1 先建立一个"哇"的认知：连压缩请求都命中缓存

第 8 章我们看缓存时说过一个伏笔：“DSH 连'让对话变短'这件事，都用缓存友好的方式去做。”现在兑现。

思考一个问题：压缩 = 让模型总结一段历史。**这个"总结请求"本身，也是要发给模型的、也是要花钱的、也是会命中/错失缓存的。**

如果你带着"缓存视角"再看压缩，会立刻注意到一个矛盾点：

> 压缩要总结的是"整段历史"，而历史是**正在变的**（对话一直在加消息）。如果压缩请求每次都从头拼 → 每次前缀都不一样 → 缓存全废 → 压缩又慢又贵。

DSH 怎么破？看 `summarizer.ts`（摘要器），它拼压缩请求的方式堪称精妙：

**压缩请求的消息列表 = 最近一次真实请求的 system + tools（原封不动！）+ 被压区域的派生消息 + 末尾追加一段压缩指令**

我们拆开看：

1. **最近一次真实请求的 system 和 tools —— 原封不动地拿来。** 这是最大的缓存保底。system 和 tools 是前缀的大头（可能占好几万 token），它们不变，意味着前缀从开头到 tools 结束这段，**和最近那次真实请求完全一致** → 缓存大概率命中。

2. **被压区域的派生消息**：要从日志里把"要压的那段"取出来，拼成消息列表。

3. **末尾追加一段"压缩指令"**：告诉模型"请把我给你的内容总结成 checkpoint，按这个结构输出"，比如：
   ```
   请按这个框架总结：Primary Request / Key Technical Concepts / Files and Code / Errors and Fixes ...
   只输出 checkpoint 文本，不要调用工具，不要提压缩这件事……
   ```

**为什么这样拼前缀就命中缓存？**
因为缓存是按"字节前缀"匹配的：请求 = [同一个 system + 同一个 tools + 一段相同的派生消息 + 唯一新增的指令尾巴]。前面一大段和"最近一次真实请求"重合，**只有末尾是新增的** → 前缀命中越大，省得越多。

> 用第 8 章的话总结：**DSH 让"压缩请求"本身成为"最近一次请求前缀的延长"，而不是"一个全新的、前缀全不同的请求"。** 这就是缓存复用魔术。

## 10.2 摘要输出要用"框"包起来：Checkpoint 格式

模型总结出来的东西，不是随意一段文字——DSH 要求它按一个**标准框架**输出，类似：

```
This is an automatically generated checkpoint condensing an earlier span of the conversation...
<compacted-summary>
  ...这里按固定章节写摘要...
</compacted-summary>
```

这套框架（Primary Request / Key Technical Concepts / Files and Code / Errors and Fixes / ...）和**你现在看到的这份教学文档**是同一个套路。

用"框"包起来（`<compacted-summary>` 标签）有实际意义：
- **可解析**：软件能识别"摘要从哪开始到哪结束"，能取出纯净内容。
- **可组装**：如果历史里已经有一份旧 checkpoint，DSH 会要求模型**把新的合并进去而不是复制**，避免越压越大。

另外有个细节：**只保留文本**。模型总结时如果尝试输出图片等非文本内容，DSH 直接抛 `UNSUPPORTED_CONTENT`——因为它只想要干净的文本摘要。

## 10.3 "摘要必须更小"：压完不能比原来大

压缩的初心是"变短"。所以 DSH 有一个硬性校验：

> **生成的摘要（加上框架包装后）的 token 数，必须小于被压掉内容的 token 数。** 否则直接抛错 "summary is not smaller than the shadowed content"。

这个校验虽然直观，但很重要——它防止"模型啰嗦地总结出一大坨，越压越大"的翻车情况。**要么真的变小，要么这次压缩作废。**

## 10.4 "重试"到底是什么意思？——重要澄清，别被坑了

第 9 章我们留了一个悬念：稳定性检查失败后会怎样？现在揭晓，而且**答案是很多人会想错的**。

### 先说：稳定性检查失败 ≠ "原地重试"

很多人（包括曾经的你可能的直觉）会以为：压缩失败（比如摘要生成中途不行、校验没过）→ 那就"重试"再压一次。

**DSH 不这样做。为什么？**

因为"稳定性失败"的本质是"**展板（Surface）已经变了**"——对话又加了新消息，或者被别的压缩动过了。如果你对**过时的展板**再压一次，那是在基于错误的信息干活，错上加错。

所以 DSH 对"稳定性失败"的处置是分场景的，每个都深思熟虑：

#### 场景 A：自动压力压缩，稳定性失败
→ **本次压缩作废**：关闭锁、记一次失败。然后**不在这里硬重试**，而是等**下一个 step 边界**再重新量长度、重新触发一次全新的压缩。

> 为什么要等下一个 step？因为对话在继续推进，等到下一轮再压时，"新消息"已经进账本了，在**新展板**上重新选段才正确。原地重试用的是旧的、错的展板——**绝不干**。

#### 场景 B：溢出压缩，稳定性失败
→ 这里有个精妙的判断：只当**确实发生了实质进展**（比如无模型裁剪器已经把工具结果削短了，`replaceGeneration` 变大了）时，才允许"重试"（返回 `{kind:'retry'}` 让上层**重新发请求**）。如果**没有任何实质变化**（压完等于没压），就**保留原始错误**，不重发。

> 为什么？溢出是"请求都发不出去/报错"的情况。当且仅当压缩**真的腾出了空间**，才值得重试请求；如果压了也没用，重试只会再报一次错，白浪费。**有实质进展才重试，没进展就认命。**

#### 场景 C：手动压缩，稳定性失败
→ 提示用户"会话在你压缩期间改变了，我这次没有提交"。**记录在案，你还可以再输入一次 /compact 重新压。** 绝不未经用户同意就压掉当前已经变化的内容。

> 三个场景的共同底线，用一句话说：
> **绝不基于"过期的 Surface"提交任何摘要；"重试"只发生在"展板确实前进了"（有新消息 OR 有实质裁剪）之后。**

这条底线，就是 DSH 对"正确性"近乎偏执的坚持。你学到的不只是机制，而是态度。

## 10.5 压缩时的"锁"与"并发"：绝不两个一起压

第 9.6 我们提过"拿锁"。这里展开讲并发保护：

- 压缩开始先检查：有没有**未闭合的 compaction/start**？有没有在"会话结束种子（end-seed）"之后又发生压缩？有 → 抛 busy（拒绝）。
- 为什么？因为两个压缩同时跑，就是对同一个 Surface 打架，谁也说不清谁压了哪段。**压缩必须是原子的（一次只来一个）。**

同时，手动压缩还要检查 Agent 是否 idle——如果不空闲，同样抛 busy。这些"宁可不做，不可乱做"的并发纪律，换来的是压缩的确定性。

## 10.6 无模型裁剪器（Tool Result Pruner）：不花钱的救命稻草

还记得压缩前有一步"先裁剪工具结果"吗？`compaction-tool-result-pruner` 就是干这个的。它**完全不调用模型**，纯靠文本规则，把超长的工具结果**机械地削短**。

它怎么工作？设定阈值：

| 参数 | 默认值 | 意思 |
|---|---|---|
| `thresholdChars` | 8192 | 超过这个长度才需要削 |
| `headChars` | 4096 | 保留开头多少字符 |
| `tailChars` | 1024 | 保留结尾多少字符 |
| `PRUNE_MARKER` | `\n\n[... tool result middle pruned ...]\n\n` | 中间被削掉的标记 |

流程：
1. 工具结果超过阈值 → 保留**开头** 4096 字符 + 标记 + **结尾** 1024 字符，中间的丢掉。
2. 保留头尾是因为：工具结果通常开头有结构信息、结尾有总结信息，中间往往最不关键。

两个值得一提的细节：
- **按 Unicode 码点切**，不会把 emoji 这种多字节字符从中间劈成两半（细心）。
- **只改 content，其他字段不动**——这呼应第 4.7 的规则"tool result 的改写只能动内容"。

### 它的流程价值：能省一次模型调用

压缩开始前，DSH 会**先用裁剪器削一轮**，然后**重新测量**：

- 如果削完之后**已经低于阈值**了 → 直接不压了（省下模型总结的那次调用！）。
- 如果还超 → 才进入真正的模型压缩。

> 这是一种"**先做便宜的事，实在不行再上贵的事**"的分层策略。很多简单的超长（尤其工具结果太长）根本不需要模型总结，裁剪一下就解决了；只有裁剪也救不回来时，才动用模型压缩。省下来的模型调用，都是白赚的。

## 10.7 一个完整的"压缩旅程"走一遍（全回顾）

```
对话加到 102,400 token（128K×0.8）
  ▼ 触发器：agent/pre-step 时自动检测到压力
  ▼ 无模型裁剪器先上：把超长工具结果削短（head+marker+tail）
  ▼ 重新测量：
      ├─ 已经低于阈值？ → 结束，今天不压了（省一次模型调用）
      └─ 还超？ → 进入正式压缩
  ▼ 拿锁：append compaction/start（拒绝并发）
  ▼ 测量 shadowedTokenCount + selectCompactableRange（尾留 16% + 平衡切点）
  ▼ 拼压缩请求：【最近真实请求的 system+tools（原封）】+【被压段消息】+【压缩指令】
       → 前缀命中缓存！ → 模型输出 checkpoint（<compacted-summary> 包着，只留文本）
  ▼ 校验：摘要 ≤ 被压内容（必须更小）
  ▼ 稳定性检查：重测量，Surface 没变？
       ├─ 变了 → 作废，关锁，等下一 step 再压（绝不过期提交）
       └─ 没变 → 提交：
           append compaction/summary（记录一切）
           append user/message（摘要，surfaceOp replace 遮蔽旧段）
           append compaction/end（关锁）
  ▼ 重新测量：< 阈值 → 成功
```
