# 第 3 章 会话事件日志：那条只增不改的"账本"

> 你即将接触 DSH 的"心脏"。这一章的内容是后面几乎所有章节的地基：
> 如果不理解"事件日志是唯一真相"，就看不懂缓存为什么珍贵、压缩为什么难做、崩溃为什么能恢复。
> 慢慢来，这一章值得读两遍。

---

## 3.1 先看一个"文明的账本"

想象你负责记录一个客栈的流水账。规矩是：

1. **每发生一件事，就往后写一行。**
2. **已经写下的行，绝不允许回头改、撕掉、覆盖。**
3. **想查任何时刻客栈是什么样，把从头到那一刻的行重读一遍就行。**

这个账本有几个神奇特性：

- **永远可信**：因为没人能篡改历史，所以你查到的每一段都可以回溯验证。
- **能从头再来**：哪怕你算错了今天的余额，砸掉缓存重新按账本算一遍，一定回到正确结果。
- **谁都能对齐**：两台机器、两个进程，只要对同一本账本重放，结果必然一致。

**DSH 的会话日志（Session Event Log）就是这本账本。** 学完这一章你会看到，DSH 里"会话"不是"一段聊天记录"那么肤浅——**它是一个事件流，每一步都被公正地记下来。**

---

## 3.2 日志里记什么样的"事件"？

DSH 把一个 Agent 会话里发生的**每一步**都记成一条事件（Event）。事件有很多种，我们挑几种：

| 事件类型 | 大白话 | 什么时候产生 |
|---|---|---|
| `user/message` | 用户说的一句话 | 用户发消息 |
| `assistant/chunk` | 模型说的一个字/一个词（流式） | 模型正在说话（逐块到达） |
| `assistant/message` | 模型说完的完整一段 | 模型说完了 |
| `tool/call` | 模型决定"调用某个工具" | 模型发出工具调用 |
| `tool/result` | 工具执行完返回的结果 | 工具执行完毕 |
| `turn/start`、`turn/end` | 一轮循环"开始"、"结束" | 循环边界 |
| `step/start`、`step/end` | 一步（一次模型↔工具来回）开始/结束 | 单步边界 |
| `compaction/start`、`compaction/summary`、`compaction/end` | 压缩流程的开始、摘要、结束 | 压缩发生 |
| `request/header`、`request/context` | 本次请求的"头"（模型/配置）和"上下文"信息 | 发请求前后 |

注意**每一条事件都带一个单调递增的序号 `seq`**。这个 `seq` 非常重要——它是"账本的页码"，后面一切引用（压缩、重放、工具配对）都靠它。

---

## 3.3 为什么"只增不改"这么重要？——三个理由

### 理由①：可重放（Replay）＝ 可恢复

假设程序跑着跑着崩了，内存里的一切都没了。怎么办？

DSH 不慌：**日志在磁盘上还是完整的**。重启后，把日志从第一条重放到最后一条，就能**几乎完整还原**出对话上下文，Agent 继续干活。这就是"崩溃恢复"。

DSH 里连最细的送代实现都是这个思路：`event-subscription-service` 兜底时，会 **每 500ms 重放一遍持久化的日志** 来补齐可能漏掉的广播。你想想——为什么它敢重放？**因为日志只增不改，重放一定得到正确结果。**

### 理由②：复现（Debug）＝ 有据可查

对话出 bug 了，用户说"模型明明给我看了一段话，但后来不见了"。

传统软件你会抓耳挠腮。DSH 呢？翻日志就能找到：那段话是 `assistant/message` 记在 seq 500 的，后来被 seq 900 的一个"替换"遮掉了（第 4 章讲 Surface 会解释"遮掉"）。**每一步都有痕迹，这是排错的神器。**

### 理由③：缓存＝ 日志的"副产品"

这是 DSH 的灵魂（第 8 章专讲）。模型服务的缓存（Prompt Cache）对**请求前缀的稳定性**极其敏感。而 DSH "只增不改"的设计，天然让前缀稳定：

> 因为历史永远不改、只会往后加——所以**每次新请求 = 老前缀（一字没动）+ 新尾巴**。老前缀在云端的缓存**大概率还在**，直接复用，省一大笔钱和大把时间。

这就是为什么 DSH 宁可做一个"账本"，而不做"可编辑的数据库"。

## 3.4 从事件日志到"对话"：一个推导过程

你可能要问：日志是一堆事件，用户看到的却是一段对话，怎么从事件变成对话？

DSH 的答案是：**写一个"投影"（Projection）函数，把事件流翻译成对话。**

最核心的翻译规则（DSH 管它叫 `deriveEventMessage`，只有一个）：

- `user/message` 事件 → 直接给出 `data`（用户消息）
- `assistant/message` 事件 → 给出 `data.message`（模型回复）
  - 但你注意：如果模型这条消息**内容为空**（只有 usage 统计，比如只是为了记 token 用量而追加的一条空 assistant 消息），那就返回 `null`，**不显示**。
- `tool/result` 事件 → 给出 `data.message`（工具结果）
- 其他事件 → 全都返回 `null`（不参与对话）

就这一条规则，决定了"模型能看到的对话长什么样"。而 `assistant/chunk`（流式碎片）是**不直接进对话投影**的——它只是原始流，等模型说完，合成一条完整的 `assistant/message` 才算数。

---

## 3.5 "日志里有什么，模型就能看到什么"——铁律一落地

还记得第 2 章那条铁律"Model-visible ⟺ logged"吗？现在它在日志层面落地了。

DSH 明确要求：**凡是该带上 `surfaceOp`（表面对话位置标记）的事件，日志里必须有它，模型才会看到它；不该带的，也绝不能乱带。** 代码里 `surfaceOpOf` 这个校验就是在执行这条铁律：

- 一个不是"表面事件类型"的事件（比如 `compaction/start`），如果它居然带着表面标记 → **抛错**（你不该有）
- 一个确实是"表面事件类型"的事件（比如 `user/message`），如果它居然没带表面标记 → **抛错**（你必须带，否则模型看不到你）

这就保证了：**模型能看到的 = 日志里明确标记为"该给模型看"的。** 不会多，也不会少，丢一个就报错，绝不悄悄漏。

## 3.6 请求头事件：`request/header` 与 `request/context`

日志里有两类"元信息"事件，你可能觉得不起眼，但它们是缓存和压缩的关键。

### `request/header`（请求头）

每次发模型请求之前，DSH 会想："这次请求用的模型是什么、配置参数是什么、system prompt 是什么、tools 是什么？"

它把这些信息记成一个 `request/header` 事件。**但关键在"记不记"是有讲究的**：

> DSH 只有在"这个 header 和上一次**真的不一样**了"时，才追加一条新的 `request/header`。一模一样？不再记。

为什么？因为**请求头 = 请求前缀的最前面那段**。缓存最怕"明明一样却重发/换了"。DSH 用 `headerEquals` 严格判断：配置、reasoningEffort、maxTokens、system、tools 逐项比较，**全都不变就不写新事件**。这既省日志，更保住缓存前缀稳定。

### `request/context`（请求上下文）

发请求时还把 `provider`（厂商）、`model`（模型名）、`contextWindow`（上下文窗口大小）记成一条。同样也是**变了才记**。

你可能觉得一个 contextWindow 记一下就行，何必区分变没变？——**因为它是压缩的"标尺"**：压缩要判断"我们现在接近窗口上限了吗"，就看这个值。第 9 章你会用到它。

## 3.7 一段"账本日记"，看完秒懂

我们虚构一小段对话，把它记成日志，你会瞬间明白"事件流"是什么感觉：

```
seq 1   user/message     用户说："帮我看看这个项目结构"
seq 2   turn/start       第 1 轮循环开始
seq 3   step/start       第 1 步开始
seq 4   assistant/chunk  "我"（流式）
seq 5   assistant/chunk  "来看"（流式）
seq 6   assistant/message 完整回复："我来看看这个项目结构"（只带这段）
                          + 一个 tool/call：调用 list_files
seq 7   tool/call        模型调用工具：list_files（参数：当前目录）
seq 8   tool/result      工具返回：["src", "docs", "package.json"...]
seq 9   step/end         第 1 步结束（有工具调用 → 还要继续）
seq 10  turn/end         第 1 轮结束后台暂停，等待下一次……
```

有没有发现？**你把它从头读到尾，就完整还原了这次对话。** 这就是"账本"。

## 3.9 下一章预告

日志是"账本"，你知道了。但**模型不能直接看账本**——它太碎了（有 `chunk`、有 `turn`、有各种元事件）。那 DSH 怎么"从账本里挑出该给模型看的那一排"？这就是第 4 章：**Surface（表面对话视图）**。那里还会出现两个你之前没见过的词——**surfaceOp** 和 **replace**。

> 记住这句话再走：
> **事件日志是 DSH 的唯一真相：只增、不改、可重放；而"模型能看到的"只是从账本里投影出来的那一刻的视图。**
