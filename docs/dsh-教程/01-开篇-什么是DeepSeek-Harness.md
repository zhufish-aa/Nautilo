# 第 1 章 开篇：DeepSeek Harness 到底是什么？

> 教学方式：每一章，我们先搞懂"**它到底要解决什么问题**"，再一步步拆开它"**怎么解决的**"。学完一章你会真正懂，而不是只记住几个名词。
> 这一章告诉你：DSH 是什么、它站在哪、为什么值得一个刚接手 AI 项目的人认真学。**读完这一章，你脑子里要有 DSH 的整体地图**，后面所有章节都是往地图上填细节。

---

## 1.1 先泼一盆冷水：你以前写的"AI 程序"可能根本不是 Agent

先问自己：你有没有写过这样的代码？

```ts
const response = await openai.chat.completions.create({
  model: 'deepseek-chat',
  messages: [ { role: 'user', content: '帮我写个排序算法' } ],
})
```

有，对吧？我也有。**但这是"一次一问一答"，不是 Agent。**

为什么？因为真正的 Agent 有一个关键特征：**它会自己决定下一步干什么**。

- 用户说："帮我部署这个项目，并把测试跑通。"
- 模型可能回答 "我需要先看看项目结构" → 然后它**自己去调一个"读目录"的工具**。
- 读完目录 → 它又决定"需要安装依赖" → **再去调一个"跑命令"的工具**。
- 装完依赖 → 它又决定"跑测试" → 再调工具……

看到了吗？**模型在每一次"对话"之间，还干了很多"执行动作"的事**：调用工具、拿到工具结果、根据结果决定下一句。这个"模型 ↔ 工具 ↔ 模型 ↔ 工具"反复循环，才叫 **Agent Loop（Agent 循环）**。

**DeepSeek Harness 就是一个帮你把这段循环跑起来的"底座"**。它不是一个聊天应用，而是一台"**能运行 Agent 的机器**"。

---

## 1.2 拆开 DSH，它其实是四层东西

我们不加修饰，直接看它由什么组成。DSH 是一个 monorepo（一个仓库装很多包），但核心就四层：

```
┌─────────────────────────────────────────────┐
│  第4层：子代理 / 压缩 / 工具 / 权限...        │  ← 各种"插件"能力
├─────────────────────────────────────────────┤
│  第3层：Agent Loop（循环驱动器）              │  ← 让循环转起来
├─────────────────────────────────────────────┤
│  第2层：Session（会话事件日志 + Surface）      │  ← 记录一切 + 算"模型该看什么"
├─────────────────────────────────────────────┤
│  第1层：Cordis（插件容器）                    │  ← 让上面所有东西能"插拔"
└─────────────────────────────────────────────┘
```

**这四层的逻辑是递进的**：

- **第 1 层 Cordis**：所有东西都是"插件"，插件之间怎么打招呼、谁生谁死，靠它管。没有它，下面全是散沙。
- **第 2 层 Session**：Agent 干活的所有过程，被记成一条**只增不改的日志**；再从日志里算出"模型下一步应该看到什么"。
- **第 3 层 Agent Loop**：在上面两层之上，真正把"发请求 → 拿工具调用 → 执行工具 → 再发请求"的循环转起来。
- **第 4 层各种能力**：压缩、子代理、工具、权限……都是挂在循环上的插件。

后面每一章，就是一层一层往下钻。

## 1.3 用一句话给 DSH 画个像

如果只能记一句话，记这句：

> **DSH = 一切皆插件 + 一条只增不改的事件日志 + 一张给模型看的视图（Surface）+ 一个尊重缓存的 Agent 循环。**

再翻译成人话：

- **一切皆插件**：想加能力？写个插件挂上去就行，不用改核心。
- **日志**：Agent 说的每句话、调用的每个工具、压缩的每次操作，全都被记下来，**永远不改，只往后加**。这是"真相的唯一来源"——出任何问题，重放日志就能重来。
- **Surface**：模型不能看到日志里所有东西（那太杂了），所以系统实时算出"模型应该看到的那一排节点"。
- **Agent 循环**：让模型和工具你来我往转起来，并且**尽量不破坏云端模型的缓存**（后面专章讲，这是 DSH 的灵魂之一）。

## 1.4 为什么你要认真学它？——三个"因为它解决了真问题"

很多人说"不就是调 API 的循环吗，我自己也能写"。但你写的时候，一定会撞上这几个墙，而 DSH 恰好已经拆过墙了：

### 墙①：上下文是有限的（Context Window）

模型一次只能"看完"那么多内容。对话长了，装不下。
**自己的方案**：粗暴丢掉前面的消息 → 模型忘了用户最初要什么，越跑越偏。
**DSH 的方案**：压缩（Compaction）——把旧历史用模型总结成一段精华，**既变短又不失上下文**。而且它压缩的时候还想着别把缓存搞坏（第 9、10 章）。

### 墙②：聊天越来越贵，钱花在哪儿都不知道

模型的计费和"缓存命中"关系极大：如果请求前缀一字不变，云端可以直接复用之前算好的缓存，又快又便宜。
**自己的方案**：随便拼提示词，每次都不一样 → 缓存全废，又慢又贵。
**DSH 的方案**：想方设法保证"请求前缀能复用缓存"，并且专门统计缓存命中多少 token（第 8 章）。

### 墙③：程序崩了 / 要复现，根本不知道当时发生了什么

**自己的方案**：打日志，打一堆，还是对不上。
**DSH 的方案**：一切都有事件记录，随时可以从日志**完整重放**出当时的对话（第 3 章）。因为它是"只增不改"，任何时候回溯都是对的。

这三个墙，是每一个认真做 Agent 产品的人都会撞上的。**学会 DSH，等于别人已经把坑踩平，你直接学会了怎么不踩。**

## 1.5 一张表，带着你认识 DSH 的"家庭成员"

下面这个仓库根目录的长相，先混个眼熟，后面章节会一个个点名。

| 目录 / 包 | 干什么的（人话版） | 对应章节 |
|---|---|---|
| `packages/core/agent-loop` | **循环驱动器**：让模型和工具转起来 | 第 5 章 |
| `packages/core/session` | **事件日志 + Surface**：记录 + 算模型该看什么 | 第 3、4 章 |
| `packages/llm/llm` | 一套不绑死任何厂商的"模型调用接口" | 第 7 章 |
| `packages/llm/llm-deepseek` | 把咱通用接口翻译成 DeepSeek 专用的东西 | 第 7 章 |
| `packages/llm/token-meter` | 数 token 的小尺子 | 第 7 章 |
| `packages/compaction/*` | **压缩全家桶**：接口、实现、无模型裁剪、命令 | 第 9、10 章 |
| `packages/subagent/*` | 能"生小 Agent"去干活 | 第 11 章 |
| `packages/interaction/*` | 权限、要用户批准、命令 | 第 11 章 |
| `packages/session/session-persistence-*` | 把日志存到磁盘（jsonl / sqlite） | 第 11 章 |
| `packages/bundle/*` | 把一堆插件拼成"完整应用" | 第 11 章 |
| `vendor/` | 固定的 Cordis 插件容器源码 | 第 2 章 |

这份表先存着，不要求你背。后面每一章都会"带你实地去仓库里看那个文件"。
