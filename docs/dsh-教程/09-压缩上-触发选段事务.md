# 第 9 章 压缩（上）：什么时候压、压哪一段、怎么保证压得对

> 前面 8 章你有了完整的地基：账本、Surface、缓存。从这一章开始，我们把 DSH 里**最复杂、最精华**的子系统——**压缩（Compaction）**拆开讲。
> 压缩要回答三个灵魂问题：① 对话什么时候"太长"该压了？② 压哪一段最划算、又不破坏结构？③ 压完之后怎么保证没把会话搞坏？
> 这一章讲①和②的主体 + 整件事怎么"事务化"地做对。第 10 章讲那个最闪光的部分（摘要前缀复用）和"重试"的深层语义。

---

## 9.1 为什么必须有压缩？

回到朴素的现实：**上下文窗口有限。** 第 8 章我们那么珍惜缓存、珍惜前缀，但缓存再厉害，也救不了"对话已经超出窗口容量"。

两种必死场景：

1. **缓慢涨满（pressure，压力）**：对话慢慢加了 8 万、10 万 token，快填满 128K 窗口了。再继续下去模型就"看不下"了。
2. **直接爆掉（overflow，溢出）**：某次请求直接超过了窗口上限，API 报出 `CONTEXT_WINDOW_EXCEEDED` 错误。

压缩就是回应：**把"旧的历史"用一段"摘要"换掉，让对话变短，又不丢失关键信息。** 但压缩必须小心翼翼，因为它会动到 Surface（→ 动到缓存、动到结构）。这就是为什么 DSH 为压缩准备了一整套精密机制。

---

## 9.2 触发器一：压力触发（pressure）——快到上限了

DSH 有一个"自动压缩"开关（`auto: true`，默认开着）。它在 `agent/pre-step`（第 5 章：每步之前）都会悄悄检查一次：

**检查什么？** 用 token-meter（第 7.7 章）量一下当前总 token 数，和"阈值"比：

```
阈值 thresholdTokens = 窗口大小(128K) × 0.8 = 102,400 token
当前多少？ totalTokens < 102,400？ → 不够长，不压，继续跑
             totalTokens ≥ 102,400？ → 够长，触发压缩！
```

所以**默认是窗口的 80% 就开始压**（thresholdRatio=0.8）。为什么不等到 100%？因为压缩本身也要拉模型跑一次，得留出余量，别压到一半就爆了。

### 触发后要"压掉多少"？
DSH 有个"保留比例"：

```
retainTokens = 窗口大小 × 0.16   （比如 128K 窗口 → 保留 ~20,972 token 不压）
```

意思是：**压掉 84% 的旧历史，保留最后 16% 原封不动。** 为什么保留最后一点？因为"最近的话"往往是上下文最有用的（模型正要基于它继续干活），保留下来让模型有最近的记忆。

---

## 9.3 触发器二：溢出触发（overflow）——直接爆了

如果模型 API 直接返回 `CONTEXT_WINDOW_EXCEEDED`（上下文窗口超限）错误，DSH 会进入"溢出处理"。

它和压力触发不同的关键点：

> **溢出触发时，retainTokens = 0。**

也就是说：**能压的全部压掉，只留下最后一条消息（用户最新输入）。** 因为此时已经爆了，没资格保留 16%，只能拼命腾地方。

它还有一个武器：先调用"**无模型裁剪器（tool-result-pruner）**"（第 10 章详讲）把超长的工具结果**直接截断**，再重测。能省就省。

> 溢出触发只在本会话**还没重试过太多**时有效（`overflowRetries` 计数），压完如果真的成功腾出空间，才允许重发一次请求；重试太多次还不行，就保留原始错误给上层。**绝不死循环。**

---

## 9.4 触发器三：手动触发（/compact）——用户主动压

用户可以主动输入 `/compact` 命令要求压缩。

手动和自动的最大区别：**手动要求 Agent 必须空闲**（idle）。因为手动压缩要动整个 Surface，如果 Agent 正在跑，会打架。所以 DSH 会先把 Agent 切到 **maintenance（维护）状态**去执行压缩，压完回来。

手动压缩同样 `retainTokens = 0`（尽可能多压）。用户要的不是"再省点"，而是"彻底清一遍"。

---

## 9.5 压缩要"压哪一段"？——选段的智慧

现在问题来了：要压，压从哪到哪？DSH 用的是 `selectCompactableRange` 算法。说人话它的步骤：

1. **从尾部往前量**：从 Surface 的最后往前数 token，数够 `retainTokens` 就停下。这标记了"这段要留、前面的可以压"。
2. **往前挪一点**：选出来的切点，还要往前检查一个非常关键的规则——**不能切在"对话对子"中间**。

### 什么叫"对话对子"？——工具配对（tool pairing）

还记得第 6 章的"tool/call 必须和 tool/result 配对"吗？压缩的切点**必须落在"配对平衡"的地方**：

> 想象从某一个位置切开，把前面的都压掉。切开后，剩下（保留下来）的部分里，**不能出现"只有 tool/call 没有 tool/result"或反过来的情况**。

DSH 用一个计数器计算"平衡性"：
- 碰到 `assistant/message` 里的 tool-call → 计数器 +1
- 碰到 `tool/result` → 计数器 −1
- 切点必须是**计数器归零**的地方（balance = 0）。

为什么？因为你把 `tool/call #3` 留着、却把 `tool/result #3` 压掉了，模型接下来就会看到"有个调用但没结果"，上下文就串味儿了（而且第 6 章会报 corrupt surface）。**切点必须落在成对收尾的地方。**

所以 `selectCompactableRange` 的实际动作是：先按 token 从尾部切 → 如果切点不平衡，就**继续往前挪**，直到挪到平衡处。宁可多压一点，也不敢在中间裂开。

---

## 9.6 压缩是一次"事务"——这是全书最严谨的一段

**压缩不是"改一下 Surface"那么简单，它是一次必须"要么全成、要么全败"的事务。** 因为中间充满风险：摘要可能生成失败、可能不小、可能对话在压缩过程中又变了。DSH 用一套"账本级事务"来保证永远不留下半截状态。

事务的步骤，像手术一样严谨：

### 第 1 步：拿锁
往账本写一条 `compaction/start` 事件，作为**持久化锁**。

- 如果检查到"已经有没关闭的 compaction/start"→ 抛 "busy"，拒绝并发压缩（不能两个同时压）。
- 这条 `start` 会一直挂在账本里，直到 `compaction/end` 关上它。

### 第 2 步：测量 + 选段
用 token-meter 量一下整个 Surface 共多少 token（`shadowedTokenCount`——即"待遮蔽"的历史总量），再按上面 9.5 选出要压的段。

### 第 3 步：让模型总结
把"要压的那段的派生消息"发给模型，让模型把它浓缩成一个 checkpoint 摘要（`summary`）。

（这里有个前提校验：**摘要必须比原文小**，如果生成的摘要居然比压掉的原文还大 → 直接抛错，绝不干越压越大的蠢事。）

### 第 4 步：稳定性检查（压缩前最惊险的一关）
这是事务的灵魂之一。**检查"我刚刚量过、选过的 Surface，现在还是这个样子吗？"**

> 因为压缩耗时（模型总结要几十秒），这期间对话可能又变了：新消息进来了、别的压缩动了它……如果按"过时的展板"去提交，就会：**用一个旧结构压掉一段本不该压的**，或者**摘要跟当前不符**。

DSH 应对：
- 自动压缩用 **whole-surface** 稳定性：把整个 Surface 重新量一遍，和开始时的深比较（deep-compare）。变了 → 视为失效。
- 手动压缩用 **selected-span**：只检查我选中的那一段还在不在、有没有变；段外面的新消息不影响我（我压的本来就不包括它们）。

**如果稳定性检查失败怎么办？** 这是第 10 章重点，但先给结论：**绝不提交过期摘要**，宁可这一轮作废、锁关闭、下次再压。

### 第 5 步：提交
一切通过，写入账本：
- `compaction/summary` 事件（记摘要、遮蔽范围 shadowedRange、遮蔽 seq 列表 shadowedSeqs、被压 token 数、用的模型、usage 等——全部留下审计痕迹）
- 然后写一条 `user/message`，内容是"checkpoint 摘要"，用 `surfaceOp: {op:'replace'}` 把选中的旧节点**整体替换**成这条摘要。

（这一步还会再校验一次配对平衡：替换的起始点和结束点都必须"平衡"，不能拆散工具对——上一轮选段已保证，但提交前再确认一遍。）

### 第 6 步：关锁
写 `compaction/end` 事件。**哪怕是失败，也要写 end（并记录错误）**——保证锁永远不被悬挂，也保证"失败的 start"能被检测到（有 start 没有 end = 异常，可定位）。

> **一句话总结事务：拿锁 → 测量选段 → 模型总结 → 确认没变 → 提交替换 → 关锁。任何一步失败，宁可作废重来，绝不留下半截账本。**

## 9.7 为什么要把"压缩"也写进账本？

你发现没有：连"压缩"这个动作本身，都完整地写进了事件日志（start / summary / end）。

这太重要了：
- **可审计**：任何一次压缩，何时发生、压了什么、用了哪个模型、花了多少 token，全可查。
- **可重放**：账本重放时，压缩也作为"事实"被重放——重放结果和真实一致。
- **可恢复**：中途崩了，`compaction/start` 没有对应 `end`，一眼看出"压缩没完成"，可以安全处理。

**压缩也是事件流里的公民，一视同仁。** 这就是"账本是唯一真相"最彻底的贯彻。

## 9.9 下一章预告

第 9 章看到了压缩的整体骨架。但还有三个最精华的细节没讲透，全在第 10 章：
1. **摘要请求怎么复用缓存**（那个"天才操作"）；
2. **稳定性检查失败后的"重试"到底是什么意思**（你会有意外收获，它绝不是"原地重试"）；
3. **无模型裁剪器**（不用调模型，直接把超长工具结果截断，省一次模型调用）。

> 记住这句话再走：
> **压缩 = 量长度(80%阈值) → 选段(从尾留16%) → 平衡切点(不拆工具对) → 模型总结(必须更小) → 验稳定性(没变才提交) → 成对入账(start/summary/end)；任何一步失败宁可作废，绝不留半截。**
