# 第 2 章 一切皆插件：Cordis 是怎么把 DSH 拼起来的

> 这一章之前，你可能默认"一个程序就是一个大文件，里面写死所有功能"。这一章要彻底改变这个观念：**DSH 是一堆积木，每一块都能单独换，而 Cordis 是拼这些积木的底座**。
> 读完这一章，你会懂——为什么 DSH 敢说"想加能力？写个插件挂上去就行，不用动核心"。

---

## 2.1 先看一个"活"的问题：没有插件系统会怎样？

假设你要写一个 Agent 应用。一开始你能想到的功能有：跟模型对话、调用工具、保存历史。

你写了一个大文件 `app.ts`，里面：
- 一个函数负责"调模型"
- 一个函数负责"跑工具"
- 一个函数负责"存历史"

一切正常。但三个月后你发现：

1. 想支持第二个模型厂商（比如从 DeepSeek 换成别的）？—— 你得改 `app.ts` 里"调模型"那段。
2. 想加一个"自动压缩长对话"的功能？—— 你又得往 `app.ts` 里塞几百行。
3. 想加"权限确认"，让用户批准工具调用？—— 继续往 `app.ts` 塞。
4. 突然发现某个插件有问题，想暂时卸掉？—— 做不到，因为都焊死在一个文件里了。

**这样的代码我们叫"耦合"**：功能之间你中有我、我中有你，牵一发而动全身。

**DSH 的选择是：反着来。** 核心只做一件事——定好"接口"和"生存规则"，然后**一切能力都是插件**，想用就用、想换就换、想停就停。

---

## 2.2 认识 Cordis：插件容器

DSH 的插件底座叫 **Cordis**（在仓库 `vendor/` 目录里有一整份固定拷贝，DSH 不依赖外网装它，自带了）。

用大白话讲，Cordis 干三件事：

| 它管什么 | 大白话 |
|---|---|
| **插件的生和死** | 一个插件什么时候"启动"、什么时候"停止"，它来安排（生命周期） |
| **插件间的借东西** | 一个插件想用另一个插件提供的功能，通过它"注入"（依赖注入） |
| **事件的通知** | 一个插件干了事，其他插件怎么"听到"（发布/订阅） |

举个例子。DSH 里有一个"压缩"插件（compaction），它想"在每次模型请求之前检查一下：对话是不是太长了？长了就压缩"。它不需要自己知道"对话现在有多长"，它只需要**告诉 Cordis：请把 'token 计量' 这个服务给我用**，然后 Cordis 就把计量服务"注入"给它。

这就是所谓 `static inject = ['llm', 'tokenMeter', 'sessions']` 这行代码的意思——一个压缩插件声明：**我要用这三个服务**。Cordis 负责把它们塞进来。

---

## 2.3 核心哲学：能力缝（Capability Seam）三件套

这是 DSH 最精华的架构思想，**务必记牢**。任何"能力"（调模型、跑工具、压缩、权限……）在 DSH 里都拆成三件套：

```
┌──────────────────────────────────────┐
│  Service Definition（服务定义/接口）    │  ← 协议长什么样
├──────────────────────────────────────┤
│  Provider（提供者/实现）               │  ← 谁真的干活
├──────────────────────────────────────┤
│  Consumer（消费者/使用者）             │  ← 谁需要用它
└──────────────────────────────────────┘
```

**打个比方**：USB 接口。

- **Service Definition** 就是 USB 的"接口规范"：一共几个针脚、电压多少、数据怎么传。**它只定义'长什么样'，不知道谁在用。**
- **Provider** 就是"充电器/U 盘/鼠标"：一个符合 USB 规范的具体设备。
- **Consumer** 就是"你的电脑"：它知道 USB 接口能用，插入任何符合规范的设备都能工作。

好处爆炸性强：**Consumer 根本不用关心 Provider 是谁家的**。DSH 调用模型，只认"llm 服务接口"；至于是 DeepSeek 实现、还是别的厂商实现，Consumer 无感。想换模型厂商？换个 Provider 插件就行，调用方代码一行不改。

仓库里这些 pattern 遍地都是：
- `packages/llm/llm` 是 **Service Definition**（一套厂商无关的调用接口）
- `packages/llm/llm-deepseek`、`llm-pi-ai` 是 **Provider**（DeepSeek/其他 的实现）
- `packages/core/agent-loop` 是 **Consumer**（真正用 llm 接口发请求的循环）

## 2.4 注册是"效果"（Effect），不是"写死"

传统的写法是：插件 A 直接在代码里 `pluginA.start()`。

DSH 的写法是：**注册是一个"效果（effect）"**。一个插件启动时，通过 `ctx.effect(...)` 或 `ctx.on(...)` 声明"我要提供什么 / 我要监听什么"。

这带来一个很大的好处：**所有注册动作都能被撤销**。插件停止时，Cordis 自动把它注册的效果全部回收，不会留下"幽灵监听器"。

想想看，如果插件写在 app.ts 里，你想停掉它就得改代码。但在 DSH 里，一个插件"启动→注册→干活的插件装好了"，"停止→注销→像没来过一样"。这正是积木式的可插拔。

---

## 2.5 waterfal（瀑布）监听器：一件事，多个插件按顺序接力

DSH 里很多动作不是"只有一个人干的"，而是"一串插件接力"。

比如"模型请求"这件事。DSH 定义了一个叫 `agent/request` 的事件。当循环要发请求时：

- 插件 A 可以先说："这个请求我要在配置里加一个参数" → 改完传给下一个
- 插件 B 接着："我还要改一下 tools" → 改完再传
- 插件 C 最后："好了，就这么发"

这种 **按顺序接力、每一棒都能接着改** 的机制，叫 **waterfall（瀑布）监听器**。

关键规则：**waterfall 监听器必须调用 `next()`**，把接力棒传给下一棒。你不调 `next()`，链条就断了，后面的插件全被卡住。这是 DSH 的一个硬规矩（写在它的 AGENTS.md 开发规范里）。

同理，`agent/pre-step`（每步之前）、`agent/request-error`（请求失败）等等，都是这种可以接力的点。

## 2.6 两条"铁律"（贯穿整个 DSH）

读 DSH 源码你会发现它反复强调两条原则，**你越往后学越会体会到它们为什么重要**：

### 铁律一：Model-visible ⟺ logged（模型看到的，必须都有记录）

**模型能看到的东西，必须完整地被记录进日志；反过来，不该让模型看到的东西，也不能出现在它眼前。** 为什么？因为"日志"是真相、是复现的依据、是缓存的根基。如果模型看到了 A，日志里却没有 A，那你回溯时对不上账；如果日志里有 B 模型却看不到，那你发给模型的请求和记录又对不上。

### 铁律二：运行时边界只由 TypeScript 类型表达，不加运行时校验

DSH 内部强调"如果你明明知道某个值一定是某类型，就靠 TS 类型保证，别再写一堆 `if (x === undefined)` 的运行时防御"。这听起来像洁癖，但它的真正意图是：**把代码写得干净、可预测、行为一致**，为上面那条"缓存友好"夯实基础。

这两条我们在第 3、4、8 章会反复看到它们落地。

## 2.7 把这一章落到仓库里看看

你现在可以去 `work/deepseek-harness` 仓库里 "实地考察"：

1. 打开 `packages/compaction/compaction-basic/src/index.ts` 的类定义：
   ```
   class BasicCompactionEngine extends CompactionEngine {
     static inject = ['llm', 'tokenMeter', 'sessions']
   ```
   —— 看，这就是 2.2 说的"声明我要用这三个服务"。

2. 打开 `packages/llm/llm/src/types.ts`，看里面定义的接口（Provider/Model/Message 那些类型）—— 这就是 Service Definition：**不碰任何厂商，只定义'通话协议'**。

3. 打开 `vendor/cordis`（Cordis 源码目录）—— 你看到的就是积木的底座本身。
