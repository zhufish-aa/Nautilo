# Nautilo 的 AI Agent 工作流

**设计提案 · 2026-11-18**　[打开可交互的界面预览](preview.html)

用户可以把一次成功的 Agent 协作保存成图，下次交给主 Agent 引用。主 Agent 也可以当场生成一张图，或把已有流程当作子图接进新图。画布和 Agent 读写同一种结构化定义。主 Agent 在发起前定好任务、角色和每个 Agent 节点的提示词，运行期间由本机引擎调度。

最小的一次派发只有两个节点。主 Agent 让 Explore 查一件事，一次工具调用就可以交出这张图。Explore 提交结果，调用方在原会话收到回执。图只有在用户展开时才占据界面。

## 1. 同一张图的三种用法

| 用法 | 主 Agent 发起时交给引擎的内容 | 实际体验 |
| --- | --- | --- |
| 引用模板 | 模板引用、任务输入、角色绑定、本次提示词参数 | 用户在任务中引用「并行排查」。默认由主 Agent 判断是否采用，用户也能明确要求按此流程运行。 |
| 临时生成 | 完整图定义与输入 | 主 Agent 可以直接写出「主 Agent → Explore」，也可以为一次复杂任务编排多个分支。 |
| 混合编排 | 含模板引用的图，以及本次新增节点、连线和提示词 | 引用「证据交叉验证」，在“存在分歧”出口接上本次专用的复核 Agent。被引用流程暴露输入和命名出口，内部节点可以展开查看。 |

启动时解析并固定模板修订、嵌套引用、提示词、角色绑定和输入，形成一次运行的快照。模板稍后发布新版本，历史记录仍可解释。运行记录可以另存为模板草稿，保留定义中的备选路径；本次选过的出口、私有会话 ID 和实际任务数据属于运行记录。

## 2. 图上真正需要配置什么

| 元素 | 可配置的内容 | 引擎的责任 |
| --- | --- | --- |
| 主 Agent 入口 | 当前调用会话、任务输入、初始出口 | 绑定当前会话，在原次工具调用中启动图。只有图明确安排主 Agent 再判断时，才开启新的模型轮次。 |
| 自动分发节点 | `kind: "dispatch"`，设置每个出口的名称和目标 | 将当前结果交给所有出口，不启动模型。一个任务的结果可同时交给多个后续任务；单个出口仍建立可追踪的汇合范围。 |
| Agent 节点 | 角色、任务提示词、输入引用、结果字段、可选出口、会话复用方式 | 解析到用户选定的团队成员、Harness 和连接，派发任务并收回结构化结果。 |
| 分派与并行 | 固定分工，或按上游返回的列表逐项派发。分别设置总实例数和同时在跑的数量 | 每个子任务有独立身份。列表项有稳定的键，相同角色可以同时执行不同问题。 |
| 汇合 | 等全部、取首个合格结果、达到指定数量；剩余分支继续还是取消 | 只等本批实际启动的分支。按分支名和列表项键保留来源，处理空列表、部分失败及目标数已无法达到的情况。 |
| 命名出口与回边 | 一个节点可以有任意业务含义的出口，每条边指定来源出口和目标。回边可带循环次数或运行期限，以及用尽时的出口 | 按提交的名字前进。A 到 B 和 B 到 A 各有自己的含义和触发条件。每次回到同一节点都生成可追踪的新实例。 |
| 子流程与返回 | 引用某个修订，将子图输出映射到调用方的出口 | 子图继承调用范围和剩余预算。返回是交付调用结果；需要再次唤起某个 Agent 时，在图上显式连出下一步。 |

**出口名由作者定义。** 同一节点内名称唯一，不同节点可以各自有“完成”。内部用稳定 ID 存连线，Agent 看到并提交本次快照里的名称。每个普通 Agent 节点默认一次选一个出口。要同时选择多个，作者显式配置多选；固定并行由分派节点一次激活其全部具名分支。这样同一个「探索」角色既能独自查一个模块，也能展开成多个实例。

**连线也要说明交付什么。** 下游可以取本轮的摘要、结构化字段、文件或证据引用，以及循环上一轮的反馈。并行改代码的节点可以绑定各自的工作区，在汇合时核对变更和冲突。两个 Agent 交换一条补充消息可以沿会话传递；触发下一次执行则要经过图上的出口。

## 3. 主 Agent 在发起前准备提示词

每个可能启动模型轮次的节点，都有一份已实例化或可确定渲染的提示词模板，包括尚未选中的备选分支和引用的子图。模板作者可以提供默认指令；主 Agent 在启动时选用、补参数，或为本次任务指定覆盖。纯分派、汇合和返回由引擎执行。

例如，针对「调查桌面端切换会话后首条回复慢」，主 Agent 给独立复核节点写好这段指令。

> 根据 {{input.question}} 和 {{incoming.difference}}，找出能区分两种解释的最小证据。提交证据引用和复核结论。证据足够时选择“完成复核”，仍缺关键材料时选择“交回判断”。

在发起时检查变量路径及其来源在每条可达路径上是否可用；可选输入要有默认值或条件绑定。在激活节点时绑定实际值，并保存该次派发真正发出的提示词。并行实例各自取得自己的列表项，循环实例取得对应轮次的反馈。只有确实需要扩展原计划时，主 Agent 才提交新的子图或修订，记录新旧版本和未启动节点的边界。

需要在多轮反馈中持续引用原始证据时，可使用 `{{steps.code.latest.result}}`，或读取 `{{steps.code.instances}}` 中按激活次序保留的合格结果。`code` 是节点 ID。每次激活都冻结当时渲染出的提示词，后续结果不会改写历史提示词。提示词里需要原样保留双花括号的代码示例时，用 `\{{literal}}` 转义开头；JSON 字符串中写成 `"\\{{literal}}"`。输入值里的代码不会被再次当作模板执行。

## 4. 工作流定义 v1 与 Agent 工具

建议使用可被 JSON Schema 校验的 JSON。画布位置、缩放和折叠信息单独保存；移动节点只改变布局。下例是一份完整的最小定义，展示一次派发和两种可返回的结论。

```json
{
  "schemaVersion": 1,
  "id": "single-explore",
  "entry": "main",
  "inputs": { "question": "text" },
  "nodes": [
    {
      "id": "main", "kind": "main",
      "exits": [{ "id": "dispatch", "name": "开始探索" }]
    },
    {
      "id": "explore", "kind": "agent", "role": "Explorer",
      "prompt": "围绕 {{input.question}} 阅读相关代码。给出可以复核的证据。已有依据时选择「已有证据」，资料不足时选择「需要线索」，并说明缺什么。",
      "outputs": { "summary": "text", "evidence": "list<text>" },
      "exits": [
        { "id": "found", "name": "已有证据" },
        { "id": "missing", "name": "需要线索" }
      ]
    }
  ],
  "edges": [
    { "from": ["main", "dispatch"], "to": "explore" },
    { "from": ["explore", "found"], "to": "$return" },
    { "from": ["explore", "missing"], "to": "$return" }
  ]
}
```

`$return` 是交回调用方的保留目标，携带所选出口和结果。`role` 是图内角色，启动绑定指定实际团队成员。v1 的字段类型包含文本、数值、布尔、枚举、列表、结构化对象以及会话范围内的产物引用。条件从已声明字段读取值，支持比较与布尔组合。设计器可将视觉编辑和 JSON 编辑往返转换。

| 组合能力 | 定义中的表达 | 执行约定 |
| --- | --- | --- |
| 选择路线 | `exitMode: "one"` 为默认，`"some"` 允许一次提交非空且互异的多个出口名 | 宣告的每个出口有一个明确目标。多选只激活本次提交的集合；后续按实际激活集合汇合。 |
| 固定或动态并行 | `dispatch: "all"` 启动全部具名分支。按项分发使用 `forEach` 的 `source`、`key`、`maxItems` 与 `maxParallel` | 6 个子问题、并发 2 表示总共创建 6 个实例，最多同时运行 2 个。每个实例绑定自己的 `item`，共享的读取材料按引用传递。成员原有并发设置仍生效。 |
| 汇合 | `kind: "join"`，`scope` 指向分派节点，`wait` 取 `"all"`、`"firstValid"` 或指定 `quorum` | 每次分派有独立批次。首个合格和阈值模式须声明剩余实例的处理方式。全部模式遇到空批次可产出空列表；要求至少一份证据时走作者指定的空批次出口。 |
| 回流和嵌套 | 回边指定 `maxTraversals` 与 `onLimit`。`kind: "call"` 绑定模板修订、输入和子图出口映射 | 超限可沿 `$return_needs_decision` 交回主会话。每个有向环都要跨过受限回边或受有限的运行期限约束，嵌套调用共享上层剩余预算。 |

汇合可以显式写 `sources: ["code", "trace"]`，表示等待这两个直接连接的节点。这样同一份结果可以交给多个下游：例如 C 只用 A 的结果，D 等 A 和 B，最后再汇合 C 和 D。每个汇合独立记录到达结果，并以同一次分派批次关联；前一个汇合不会消耗后一个的来源。显式来源模式下，回路要回到 `scope` 指定的分派节点，开启新一批实例。按列表分派时，先用按项汇合收齐本批各项，再把结果交给按节点来源的汇合。

提示词中的 `input.question` 读取任务输入，`incoming` 读取本次进入该节点的证据，`item` 读取本实例的分派项。`exit.<id>` 在派发时解析为当次修订里的出口名，画布改名后，相应提示词仍能给出准确选项。

| 拟议工具 | 约定 |
| --- | --- |
| `agenthub_workflow_run` | 传 `ref` 或 `definition` 其一，以及 `inputs` 和所需 `bindings`。混合图在 `definition` 内引用子图。验证成功后立即返回运行 ID，执行过程通过事件送回会话。重复提交同一次启动请求返回原运行 ID。 |
| `agenthub_workflow_submit` | 子 Agent 提交 `branch` 与 `result`，多选节点使用 `branches`，并回传本次派发提示词给出的 `instanceId`、`attempt`。例如 `{"instanceId":"本次实例 ID","attempt":1,"branch":"已有证据","result":{"summary":"延迟出现在首个模型事件之前","evidence":["trace-17"]}}`。引擎仍从后台绑定的执行上下文确定权限；回传身份用于拒绝旧轮次迟到的提交。原生 MCP 中工具可以显示为带命名空间的 `workflow_submit`。 |
| `agenthub_workflow_status` | 主 Agent 随时查询运行、节点和待处理事项。完成、异常或明确的主 Agent 决策点可以直接唤回主会话。 |

发起前校验 ID、出口名和目标、可达性、输入输出映射、角色绑定、并行汇合范围，以及回路或递归的终止条件。多出口 Agent 负责语义判断，例如“证据冲突”；确定性规则节点可以直接从结构化数据选择出口，例如“候选列表为空”。技术故障另走异常策略，业务上的“发现反例”本身是一次成功的提交。

### 节点工作区与验收

Agent 节点可设置工作区策略。例如，下列策略要求使用独立 Git 工作区，只允许修改源码和测试目录，并执行项目必需的验收项：

```json
{
  "workspace": {
    "mode": "isolated",
    "allowedPaths": ["src/**", "tests/**"],
    "verificationTemplates": []
  }
}
```

省略工作区策略时沿用项目设置。设置路径范围也会要求 Git 隔离，路径检查包含 Agent 自己提交的变更、暂存内容和未跟踪文件；项目位于仓库子目录时，修改兄弟目录也会被检查。路径范围用于验收变更，文件访问权限由执行端和项目现有权限机制控制。

省略 `verificationTemplates` 表示沿用项目登记的全部节点检查；显式空数组表示不选择可选检查；非空数组选择该项目登记、作用域为 `task` 的检查 ID。项目必需检查始终合并执行，未知 ID 在启动前拒绝。合并候选与最终流程验收仍分别执行项目的 `merge`、`run` 检查。

独立执行先固定 Git 起点。节点在各自目录完成工作，通过节点验收后，其提交先合到候选工作区，候选通过合并检查才进入流程的汇总分支。子流程共享父流程的汇总分支；最终通过验收后，由用户查看保存的差异，决定合入原项目或保留独立成果。合入前重新核对原分支、起点、工作树与已验收的提交，保留执行期间产生的用户修改。验收中的停止会取消在途检查；重启后无法确认的外部执行保留为待核对状态，避免自动重跑产生副作用。

## 5. 引擎怎样接管，怎样防止卡住

**流程引擎**决定下一步激活哪些节点、等谁、沿哪个出口前进。**执行层**把一次节点激活落实到真实的成员、会话、Harness、工作区和 Run，接收原生轮次结束、失败、审批、工具调用与取消信号。两层可以位于同一个 Rust daemon。主 Agent 发起后，普通连线和汇合都在本机推进。

一个节点有两个独立事实，即“有一份合格提交”和“该轮执行及必要的验收已完成”。工具提交先到时立即记录并给回执；轮次先结束时给在途事件一个短暂的对账窗口。两项都满足才推进下游。Harness 常驻进程可以继续服务其他轮次。

| 观察到的情况 | 后续动作 |
| --- | --- |
| Agent 正在推理、工具仍在跑、等待用户审批 | 显示真实等待对象。长时间无进展时检查活性，按执行期限处理；只有已经结束且缺少提交才启动补交流程。 |
| Agent 本轮已完成，只留下一句自然语言 | 进入“待补交”，持久化下一次提醒时间。向**原子会话**发起一个补交轮次，附缺失字段、合法出口和已有产物。提示它沿用已经完成的工作。画布和主会话同时能看到提醒状态。 |
| 出口拼错、结果缺字段 | 当场返回合法出口、缺失字段和可重试回执。收到有效提交、取消或升级后，立即撤销待发提醒。 |
| 收不到有效提交、进程失败、原生会话无法恢复 | 采用节点配置的异常出口或恢复策略。建议起始配置为轮次结束后给在途事件 3 秒、最多补交 1 次、补交窗口 60 秒，均可按 Harness 调整。耗尽后将已有结果和原因交回主 Agent。主 Agent 暂不可用时，记录可恢复的异常终态，依赖分支清楚显示受阻。 |
| 合法结果被重复提交、旧尝试的迟到结果抵达 | 同一实例同一尝试的相同提交返回原回执。冲突与迟到消息保留审计记录。只有当前有效尝试可以推进图。 |

补交、技术重试和业务循环分别计数。提醒同一 Agent 补一个出口不会重新跑上游。某个探索节点异常时，其他独立分支可以按策略继续；若汇合所需数量已无法达到，汇合立即转入异常处理。

**提醒是主动送达的会话消息。** 第一条由引擎发给原子 Agent 并请求一次补交，正文列出合法出口、缺失结果和已保存证据。仍超时时，第二条由引擎主动投递给原主 Agent，带上已提醒次数、等待时长、可复用的结果和可选恢复动作。两条消息都出现在执行页的消息记录里，记录“已入队、已投递、已补交或已升级”。同一实例、同一尝试、同一级别有唯一投递键。断线重连后先对账回执再补投，尊重原审批和取消状态。用户可单独开启“需要我处理时通知我”，桌面端可发系统通知、已连接的移动端可同步待办；点击定位到对应节点。原型中的收发方和消息内容均为本地模拟。

运行状态以追加事件记录。一次激活有独立的实例 ID，关联父运行、分派批次、列表项或循环轮次、执行尝试、原生会话及 Run。接受提交、完成节点与派发下游各有幂等标识；完成事件和下游待派发记录在同一事务写入。引擎重启后先对账原 Run，再恢复就绪任务与提醒。对于已经可能产生副作用、而 Harness 无法确认是否执行的派发，留下“执行结果待确认”并交给恢复策略。用户停止运行后关闭新派发与提醒，逐个核对在途中和仍在跑的实例。

### 实现时的四类持久化记录

| 记录 | 最小内容 | 读取者 |
| --- | --- | --- |
| 流程修订 | 定义、结构版本、角色要求、公开输入和出口；布局另存 | 图编辑器、模板解析器 |
| 流程运行 | 调用方会话、解析后的快照、输入、状态、各项预算 | 主 Agent、执行页、恢复服务 |
| 节点实例与尝试 | 批次、分项键、轮次、执行身份、实际提示词、Run ID、提交内容、验收与截止时间 | 流程引擎、Harness 执行层、节点检查器 |
| 待投递动作与回执 | 唯一动作键、收件会话、投递类型、下次尝试时间和送达状态 | 本机派发器、补交计时器、消息记录 |

调度器每收到一个节点事件就计算它能放行的后继。一个分支的首份有效结果可以立即激活后继，其余慢分支按图上策略处理。现有编排代码的子任务启动、原生会话与结果回传可以复用；整批计划执行及主 Agent 的派发确认回合应接成图事件，避免每经过一条普通边都再次唤起主 Agent。[现有调度实现](../../rust/nautilo-core/src/application/orchestration_service.rs)

`submissionPolicy` 可按节点设置在途对账时长、两次提醒间隔、最多补交次数与总截止时间。工具能力不足的 Harness 可显式协商同样包含 `branch` 和 `result` 的结构化终局回执，并经过相同的验证与去重。若执行端无法可靠地交付两者，角色绑定时即显示缺失能力，由作者选择合适成员。

## 6. 设计画布与执行现场

两个视图使用同一套节点、连线与空间位置。设计时回答“流程允许怎么走”，执行时回答“现在谁在做什么、为何走到这里、我需要介入吗”。[打开独立演示](preview.html)

| 设计态 | 执行态 |
| --- | --- |
| 画布居中，具名出口直接写在线旁。选中节点，在下方编辑职责、提示词、输入、结果和出口。并行节点可配置派发数量及并发上限。 | 保持画布位置，已走路线留下痕迹，正在工作的节点显示状态文字和形状。下方查看该实例的真实提示词、结果、回执和子会话。 |
| 拖动节点时连线跟手。正式编辑器支持拉线、改接、撤销、复制、键盘移动和自动排版；复杂子图可折叠成一个具名节点。 | 并行实例默认收成“已交 2/5”并可展开；回边标出当前轮次。异常定位到具体节点。顶部汇总运行状态，底部按事件定位或回放。 |
| 编辑时检查悬空出口、缺提示词、回环没有退出条件等问题，提示就放在有关端口旁。 | 日志回放和真实运行使用不同控制。暂停回放仅影响显示，暂停调度影响新派发，停止运行还需要处理在途实例。 |

**视觉沿用 Nautilo 的黑白体系。** 默认画布是纸白色，判断节点用墨黑，深色主题反转明度。并行 Agent 共用细虚线分组框，汇合用菱形，返回用胶囊形。属性放在画布下方的检查区，给主线和回边留出空间。选中节点会强调相邻连线，悬停一个命名出口可以单独追踪对应线路，点击目的地可定位下游。拖动节点有对齐参考线并可撤销，提示词中的输入变量与出口在阅读时显示为可辨认的字段。

**执行期间持续流动。** 活动线路上有带渐隐尾迹的黑白光点，浅色主题用墨色轨迹和白色光芯，深色主题用银白轨迹和深色光芯。并行时两路同时流动，汇合后沿下一条线合流，复核时沿回边折返。光点表示该实例仍活跃，同一条线上经过多次只对应一次派发。已走路线留下灰色痕迹。暂停回放定住相位，恢复时从原处继续，结束后留下静态路径。漏交用虚线轮廓、铃铛图标和反色文字标签表示，时间线上留下菱形提醒标记；会话消息展示收件人、正文和补交状态。减少动态效果时仍可凭线宽、箭头、形状与文字辨别进程。键盘可选择、移动节点与逐步回放。

### 预览里的例子

两名 Explore 分别检查代码调用链和运行时序。两份证据汇齐，综合 Agent 可以交回结论，也可以沿「证据冲突」派独立复核。复核结果回到综合节点的新一轮，先前的两份证据继续可用。预览用示例事件演示直达结论、复核回流、漏交后补交或升级；正式产品的数据源为 daemon 事件。

打开预览后可以拖节点、改提示词及出口名，再点「试运行」。在「执行」中选择「提醒后仍超时」，可以依次看到引擎给原子会话的补交通知和给原主会话的升级通知。点「会话消息」能回看正文。点时间线可跳到任意事件；暂停后选择节点，可核对它在当时实际拿到的提示词。

## 7. 能覆盖哪些 AI 协作

| 协作方式 | 搭图方式 |
| --- | --- |
| 快速探索 | 两节点图。Explore 自选“找到”或“缺线索”，主 Agent 在原会话收结果。 |
| 多个独立方案择优 | 向不同角色分发同一目标，各自生成方案。比较 Agent 等候合格候选，选“采用”“需要新方案”或“组合两案”。 |
| 拆分调研并交叉验证 | 主 Agent 给出问题列表，同一探索角色按项派发。每项保留来源；综合 Agent 只把有分歧的证据送去复核。 |
| 多轮写作与修订 | 执笔、事实核对、风格评审分别接受不同输入。“缺引用”去补查，“结构需调整”回执笔。同一草稿的修订保留脉络；独立评审可使用新会话。 |
| 编程与反证 | 实现 Agent 和测试设计 Agent 并行，复核 Agent 读两者产物。测试失败可回实现；环境不可用可交回主 Agent。工作区、验证结果与具体尝试对应。 |

允许子 Agent 自行提出细化子图时，在父节点上显式配置权限、深度和预算。新子图也要先提交完整的节点提示词，并沿父图约定的出口交付。各 Harness 原生自行派发时，以提供的事件和身份信息展示实际可观测的子任务；需要承诺出口契约与恢复能力的节点，使用 Nautilo 管理的工作流派发。

## 8. 在 Nautilo 中的落点与验收

现有团队计划支持直接处理、派发一个任务和计划多个任务。Rust 调度器已能按依赖及成员并发设置启动任务、取得子会话、等待 Run 并回传结果。当前任务依赖会做无环校验，现有图抽屉按任务依赖绘制。工作流中的显式回边，应产生新的执行实例；保留普通任务依赖原有的无环语义。[领域模型](../../packages/domain/src/index.ts) · [编排服务](../../rust/nautilo-core/src/application/orchestration_service.rs) · [依赖校验](../../rust/nautilo-core/src/runtime/orchestration/decision_validator.rs) · [现有图视图](../../apps/desktop/src/renderer/src/features/sessions/Drawers.tsx)

按 Electron + React、Rust daemon 的现有架构实施。定义与 IPC 契约放在共享 domain/schemas，运行事件放在 event-protocol；Rust 的应用服务协调图运行、仓储和既有 Harness 执行层，Node 对照 daemon 同步协议。现有 `agenthub_delegate`、`agenthub_plan` 保留调用形状，在覆盖原有审批、回执和会话身份后，分别转换为最小图与依赖图。普通的“主 Agent 自己处理”无需额外生成一次委派。旧记录继续按已有任务事件展示。[项目分层约定](../adr/0001-core-daemon-boundaries.md) · [原生工具名称](../../rust/nautilo-core/src/runtime/orchestration/runtime_tool_names.rs)

| 交付顺序 | 可实际验收的结果 |
| --- | --- |
| 1 · 跑通一张真实小图 | 任选一个具备所需能力的 Harness，完成两节点派发、命名出口、原主会话回执。主动漏交、重复提交、提交后断线、daemon 重启、取消各测一次。模板和临时定义产生相同轨迹。 |
| 2 · 跑通本预览的复杂图 | 两名 Explore 并行、汇合、条件复核、回边与用尽出口。测乱序完结、迟到回执、空批次和部分失败，并确认循环只重跑经过的节点。 |
| 3 · 用户可以自己搭建 | 完成创建与连线、提示词预览、导入导出、模板修订、会话引用、执行图与历史回放。键盘、浅深主题、缩放和减少动画都能辨认活动分支。 |
| 4 · 扩展组合能力 | 多选出口、动态分派、不同汇合策略、嵌套模板与临时覆盖逐项验收。以具体 Harness 实测工具调用、会话续用和恢复行为，展示支持范围。 |

验收的终点是用户能看着一次真实执行，说清主 Agent 事先给每个角色安排了什么，这次为何走了这条路，以及某个 Agent 没交结果时由谁接手。
